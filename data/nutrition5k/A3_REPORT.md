# A3 — 整餐視覺校準錨點報告

程式：`src/download_nutrition5k.py`（下載）、`src/meal_similarity.py`（CLIP 索引+最近鄰查詢）

## 資料

從 Nutrition5k 公開 GCS bucket 用 HTTPS JSON API 直接列表/下載（不需要 gsutil），只抓俯視 RGB 照片跟 metadata CSV，不下載影片/深度資料。實際下載 3,456 張，扣掉少數傳輸中損毀的檔案，成功建索引 **3,444 道菜**。索引：CLIP(`openai/clip-vit-base-patch32`) 圖片 embedding(512維) + cosine similarity，存成本地 `.npz`（7MB）。

## 踩到的一個 API 版本 bug

`transformers` 這個版本的 `CLIPModel.get_image_features()` 回傳格式跟舊版不同——不是直接回傳投影後的向量，而是回傳一個 `BaseModelOutputWithPooling` 物件，真正的 512 維圖片向量要從 `.pooler_output` 屬性拿。一開始直接用 `features[0]` 拿到的其實是未投影的 patch token 序列(shape `(1,50,768)`)，維度完全不對，跑相似度比對直接報錯。修正後拿到正確的 512 維向量，索引重建成功。

**最能說明價值的案例是 `images (6).jpg`**：這張照片辨識出的品項全部落在「查無資料」，已知品項加總是 **0 大卡**——如果沒有校準錨點，這餐的回覆會完全沒有熱量資訊，對使用者毫無用處。加上校準錨點後，至少能給「約 212 大卡（範圍 160～945）」這個有真實資料支撐的量級參考，雖然不精確，但遠比什麼都沒有有用。

其他案例的錨點中位數普遍落在 350～560 大卡，比已知品項加總(平均約 140 大卡)高出不少，兩者的落差誠實反映了資料庫還查不到的主菜(通常是複合菜餚)貢獻了多少熱量——這正是 C4 設計要呈現給使用者的東西，不是把兩個數字混在一起假裝精確。

## 已知限制（誠實告知，不誇大這個方法的準確度）

- Nutrition5k 是美式自助餐廳的菜色，跟台灣便當的視覺特徵(白飯+多樣小菜+醬料)有明顯落差，錨點區間普遍很寬(常常橫跨 300~900 大卡)，只能當「大概量級」參考。
- 目前只索引了 3,444 道菜（下載過程中部分照片因網路問題損毀，未重試補齊），沒有用到完整的 ~5,000 道菜。
- 相似度分數落在 0.75 上下，不算非常高的視覺匹配度——這是誠實的相似度分數，不是刻意調高的數字。
