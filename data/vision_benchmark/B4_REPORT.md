# B4 — 多模型集合辨識與投票評分報告

程式：`src/food_recognition_ensemble.py`（`recognize_food_ensemble()`）

## 關鍵 bug：qwen3-vl 預設「思考模式」會讓辨識完全失敗

第一輪测试，`qwen3-vl:8b` 10 張裡 8 張直接失敗（回傳空清單）。查 Ollama 伺服器 log 發現：模型把整個 context window（就算加大到 8192）全部拿去做內部「思考」（`<thinking>` 推理），從頭到尾沒有進入實際生成最終答案的階段，直接被截斷（`truncated=1`）。這是 Qwen3 系列思考模式的已知特性，不是 prompt 或圖片的問題。

**修法**：在 prompt 前面加 `/no_think`（Qwen3 官方支援的關閉思考模式指令），只在模型名稱含 `qwen3` 時才加，不影響 `minicpm-v`。修好後：
- 回應時間從「永遠生不出答案」變成正常的 20～50 秒
- 10/10 兩個模型都能正常回應

這個 bug 如果沒抓到，會直接讓人誤以為「qwen3-vl 這個模型不能用」，但其實只是没找到關掉思考模式的開關。

## 投票結果：成功驗證並修正了 minicpm-v 的「套模板」偏誤

重新測試 10 張真實便當照片，最有價值的發現：**`minicpm-v` 幾乎每張都講「糖醋排骨」（10 張裡 8 張），但 `qwen3-vl` 給的答案完全不同**（烤雞腿、溏心蛋、涼拌捲心菜、燉肉、醃蘿蔔……），兩者對主菜的判斷經常完全不一致。

投票機制正確處理了這種分歧：
- 當兩個模型都認同時（如「白飯」「炒青菜」「玉米」「毛豆」），標成「共識品項」，高信心度。
- 當只有 `minicpm-v` 講「糖醋排骨」而 `qwen3-vl` 講別的東西時，兩邊都被標成「單一模型」，信心度自動降低——**沒有因為某個模型講得比較「有自信」就照單全收**，這正是集合投票要解決的問題：B2 報告點名的套模板偏誤，現在會被系統自動偵測並降級，而不是靜靜地被當成事實端給使用者。

品項名稱的字串相似度分群（如「紅椒/彩椒/黃椒」「雞腿/炸雞塊/炸雞腿」「白米飯/白飯」）在這個規模（每張照片 5~12 個品項）運作良好，沒有出現明顯的誤分群或漏分群。

## 新代價：辨識時間變成原本的 2 倍以上

單模型（`minicpm-v`）平均 3～4 秒，集合辨識（兩個模型依序呼叫）變成 **25～60 秒**，其中 `qwen3-vl:8b` 本身（即使關閉思考模式）就比 `minicpm-v` 慢不少。這會影響 D2 的 LINE 整合——LINE 的同步 `reply` API 有時效限制，25~60 秒有機會超過，正式串接集合辨識時，可能需要改用 LINE 的非同步 `push` API（先回一句「處理中」，算完再用 push 送結果），而不是原本假設的單次同步回覆。這件事留給之後接回 D2 時處理，這次先不動 `line_bot.py`。
