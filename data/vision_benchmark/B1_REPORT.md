# B1 — Ollama 多模態模型選型報告

測試環境:RTX 5070 Ti (16GB VRAM)、Ollama 0.33.3。測試集:10 張便當照片(`refer\便當`,多為網路圖庫照,非手機實拍,結論的「準確率」僅供模型間相對比較,不代表真實使用情境的絕對準確率)。

## 結論:選用 `minicpm-v`，排除 `llama3.2-vision`，`llava` 列為備案

## 各模型結果

### llama3.2-vision — 無法使用(環境不相容，非 prompt 問題)

10/10 全部回傳 HTTP 500。查 Ollama server log 發現根本原因：

```
llama_model_load: error loading model: unknown model architecture: 'mllama'
```

目前這個 Ollama 版本(0.33.3)的推論後端不支援 `llama3.2-vision` 用的 `mllama` 架構，模型載入階段就失敗，跟怎麼呼叫 API 或下什麼 prompt 完全無關。要嘛換一個支援 mllama 的 Ollama 版本，要嘛放棄這個模型——建議直接放棄，不值得為了單一模型做版本管理。

### llava — 格式不穩定，內容偏籠統

- 10 張中 8 張正常回傳、能解析成合法 JSON，2 張陷入**無限重複輸出**(不斷吐「雞肉」「蔬菜」直到被 token 上限截斷，耗時 27~32 秒，遠高於正常的 5~6 秒)。
- 額外測試：把輸出格式改成強制 JSON schema，**沒有解決重複問題，反而更嚴重**(同一張圖片重複輸出「大」當份量長達 26 秒)。
- 內容品質偏保守籠統：大多只給「雞肉/米飯/蔬菜」這種泛稱，很少講出具體菜名，跟資料庫比對時可用的資訊量較少。
- 語言：正確使用繁體中文。

### minicpm-v — 內容最準確、速度最快，但輸出格式需要額外處理

- 10/10 都正常回傳，沒有重複輸出的問題，平均約 3~4 秒(llava 正常情況下也要 5~6 秒，還可能飆到 30 秒)。
- 抽測 2 張實際核對，辨識明顯比 llava 具體且準確：
  - 炸排骨便當 → 認出「玉米、四季豆、紅辣椒」還附上「白飯半碗」的份量判斷
  - 滷味便當 → 認出「紅燒肉、胡蘿蔔、白米飯」，方向都對
- **兩個已知問題，會影響 B2 prompt 設計**：
  1. 輸出不是純 JSON，前面會加一段中文說明、包在 ` ```json ` code fence 裡，甚至結尾偶爾多一句提醒——這次測試 10 筆的 `parsed_ok` 全部顯示 false，但檢查 `raw_response` 後確認**JSON 內容本身是對的**，只是外層包了文字，是解析腳本沒處理這種情況，不是模型輸出壞掉。B2 要做的是寫更穩健的擷取邏輯(從文字中找出 JSON 區塊),而不是靠模型自己只吐 JSON。
  2. 全部 10 筆都用**簡體中文**回答，即使 prompt 已經明確要求「繁體中文」。這會直接影響 C1 檢索——資料庫(`nutrition_db`／`portion_reference`)是繁體中文，簡體字串直接比對會找不到品項。B2/C1 需要加一道簡轉繁的正規化步驟(例如 OpenCC),不能只靠 prompt 要求。
- 額外測試：強制 JSON schema 模式下，模型直接放棄辨識、回傳空陣列 `{"items": []}`——比亂猜還危險，容易被誤判成「照片裡沒有食物」。**minicpm-v 不能用 schema 模式**,一定要用自由輸出 + 後製解析。

## 給 B2 的具體待辦

1. 用自由文字輸出(不要用 `format` schema 參數),靠 prompt + 少量 few-shot 範例引導格式。
2. 寫一個能從自由文字中找出 JSON 區塊的擷取器(找最外層 `{...}` 或 ` ```json ` 區塊),不要假設回傳內容從頭到尾都是純 JSON。
3. 加一道簡體→繁體正規化(如 OpenCC),放在辨識結果進入 RAG 檢索之前。
4. `llava` 保留當備案：如果之後要在資源更吃緊的環境跑(minicpm-v 5.5GB vs llava 4.7GB 差異不大,這點意義不大),或 minicpm-v 出現其他問題時再切換,但預設用 minicpm-v。
