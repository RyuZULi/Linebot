## ★ F4. 同事按了選項，助手卻說「選項已過期」

### 現象
- 為了方便一起測試，把兩位同事拉進同一個 LINE 群組使用 CEC_API助手。
- 同事 A 說某個功能「壞掉了」，助手回問「發生什麼狀況？」並列出選項按鈕。
- 同事 B 按了其中一個選項，助手回：「剛才的選項已經過期了，麻煩再描述一次遇到的狀況。」
- B 只好照著清單把選項文字一字一字打出來，其中一句「鋼構、機電、連結檔有算嗎？」因為含「機電」，
  還被誤判成機電 API 的問題，轉介給機電窗口。

### 原因
- 程式用「**發言的那個人**」來記對話狀態（目前在聊哪個按鈕、回問了哪些選項）。
- 一對一聊天時，發言的人＝這段對話，沒有問題；但在群組裡，大家看到的是**同一串對話、同一組按鈕**。
- B 按的是 A 收到的選項，程式去找 B 的紀錄，當然什麼都沒有 → 判斷成「過期」。

### 怎麼查出來的
- 問答紀錄裡沒有「過期」那一筆：當時過期的分支直接回覆，沒有寫進紀錄。
- 改對照伺服器的請求時間：09:49:01 助手給 A 選項 → 09:49:21 有一筆請求沒有對應的紀錄 →
  09:49:28 一個**從沒跟助手說過話的帳號（B）**，打出了 A 的選項 1 原文。
- 一開始猜錯了方向（以為是電腦版 LINE 看不到按鈕），使用者補充「兩位都用電腦版，而且按得到」之後，
  才對出「另一個帳號看得到 A 的選項」→ 兩人在同一個群組。

### 修法
1. 對話狀態改以「**聊天室**」為單位：群組用群組 ID、一對一用個人 ID。
2. 順帶修正測試中發現的其他問題：
   - 回問訊息本文列出編號，可以直接輸入編號或照打選項原文（同仁真的會照清單打字）。
   - 點過一個選項後，其他選項不會立刻失效。
   - 問題幾乎就是本庫常見問題原文時（相似度 ≥ 0.90），不再因為含「機電」被轉介。
   - 過期、重設等路線也寫進問答紀錄，下次出問題查得到。
3. **使用規範**：CEC_API助手設計上就是**一對一**使用。群組裡互相問，LINE 上的對話紀錄太亂，
   之後不會在群組使用；群組支援只是修 bug 的副作用，不再為群組情境加功能。

### 學到
- **測試情境本身也會造成 bug**：只是為了方便拉同事進群組，就碰到了設計時沒想過的使用方式。
  但也因此提早發現「狀態跟著人走，還是跟著對話走」這個設計假設。
- **紀錄要涵蓋所有路線**：「沒寫進紀錄」的分支出事時最難查；這次是靠伺服器請求時間反推出來的。
- **先問清楚使用者的環境，再下結論**：第一次的推測（電腦版看不到按鈕）跟實際情況不符，
  使用者一句補充就推翻了。跟 F1-2「先釐清狀況再回答」是同一個道理——這次是開發者自己也要做到。

## F5. 提到「機電」就被轉介，但其實是在追問目前的按鈕

### 現象
- 正在問「干涉風險匯出隱含碳」，接著問「那機電管線的元件也會算進去嗎」，
  助手只看到「機電」兩個字，就回「不在建築 API 範圍，請找機電窗口（機電窗口）」。
- 但這正是這個按鈕的常見問題（答案：不會算機電元件），該回答的是建築 API 的負責人。

### 修法
- **先判斷是不是新問題**：正在聊某個按鈕時，提到「機電／土木／雲端」先當成追問；
  只有明確問別的產品（「機電的 API」「MEP 的按鈕」）或帳號登入（「Revit 登不進去」）才轉介。
- **找誰依按鈕所屬類別**：有話題時，給模型的聯絡人表只留那個按鈕的類別（目前全是建築 API → 建築 API 負責人）；
  授權、安裝這類通用問題各有負責人，不限縮。
- 回歸測試直接檢查「送給模型的提示詞」裡有霽倫、沒有機電窗口，不只看最後的回答。

### 學到
- 關鍵字轉介是「沒有上下文」的判斷；有了對話記憶之後，同一個詞在不同情境下意思不同，要先看話題再看關鍵字。

## F6. 模型把按鈕名稱寫錯一個字——決定「先不修」

### 現象
- 實測回答出現「干**擾**風險匯出隱含碳」，正確是「干**涉**風險匯出隱含碳」。內容本身正確，下面也附了正確的說明頁連結。

### 考慮過的修法
- **逐詞取代（干擾→干涉）**：會誤改正常用詞（「管線互相干擾」），而且每發現一個錯字就要再加一條，越修越臃腫。
- **通用比對**：回答中某段文字跟按鈕名稱同長度、只差一個字才修正，不會越加越多，耗時只有幾毫秒。

### 決定：先不加
- 影響小：錯一個字不會讓同仁做錯事，說明頁連結是對的。
- 頻率未知：目前只看到一次，為偶發小錯多加一層後處理不划算。
- 有資料再決定：每個回答都有 👍／👎、問答紀錄存了完整回答，累積後統計實際發生頻率，真的常見再用通用比對處理。

### 學到
- **不是每個發現的問題都要立刻修**。修之前先問：影響多大？多常發生？修法會不會讓系統更難維護？
  前面幾次（錯誤訊息改字串比對、規則放提示詞後面）都有實測數據撐腰才改，這次沒有，所以先記錄、觀察。

## ★ F7. Belfast：對話被打斷，「該拿到的答案」就不見了

### 現象
- 拍照估算後，Belfast 給出兩種熱量（逐項加總／外觀參考）和確認按鈕。
- 主人說「細節」看了明細之後，想記錄熱量卻沒辦法——按鈕不見了，打數字也被當成一般聊天。
- 同樣的情況：中途問別的問題（例如「衛福部的資料是哪來的？」），回答完就沒有人記得這餐還沒記錄。
- 按了「手動輸入」之後改問別的問題，Belfast 會一直回「看不懂熱量」，等於卡住。

### 原因
- **LINE 的快速回覆按鈕只要聊天室出現新訊息就會消失**，估算其實還暫存著，只是沒有入口可以完成。
- 程式只設計了「估算 → 馬上選」這條直線流程，沒想過中間會被打斷。
- 確認訊息寫著「知道實際熱量直接告訴我」，但實際上要先按「手動輸入」才有用——說明跟行為不一致。

### 修法
1. **主動提醒**：估算還沒確認時，不管中間回答了什麼，最後都補一句「對了，主人，剛才那一餐還沒記錄喔」，並重新附上確認按鈕。
2. **打字也能完成**：直接輸入「逐項」「外觀」「不記錄」，或「500」「炒麵 480 大卡」就能記錄；問句（「這個 500 大卡怎麼算的？」）不算。
3. **不會卡住**：按了「手動輸入」卻改問別的，照常回答再提醒。

### 同一個想法也用在 CEC_API助手
- 對話記憶從 15 分鐘延長到 **1 天**：同仁中午問一半、下午回來接著問很常見，15 分鐘太短。
- 不設成無限期：隔天還延續昨天的話題容易把新問題誤判成追問；回答最後會標示延續哪個按鈕，不對就講按鈕名稱換話題。

### 學到
- **對話不是一條直線**。真實使用時，使用者會插話、追問、離開再回來；
  bot 要記得「還有什麼事沒完成」，並在適當時機主動拉回來，而不是等使用者自己想起來。
- 這跟 F1（記住目前在聊哪個按鈕）是同一類問題：**狀態要能撐過中斷**。

## ★ F8. 「車道要怎麼建」找不到——被誤當成上一個話題的追問

### 現象（同事實測，17:11～17:15）
- 先問「要怎麼略過檢查」→ 話題設為「依列表選取物件」。
- 接著問「車道怎麼用」「車道要怎麼建」→ 助手回「這個問題我沒有資料」，同事按了 👎。
- 直到打出完整按鈕名稱「建置車道」才查到。

### 原因
- 句子裡沒有完整的按鈕名稱（按鈕叫「**建置**車道」），程式就把它當成目前話題的追問，
  只在「依列表選取物件」那張卡片裡找，當然找不到。
- 這是 F1（記住話題）的副作用：記憶讓追問變順，但也讓「沒講全名的新問題」被困在舊話題裡。

### 試過、不採用的做法
- **名稱比對再放寬**：去掉開頭的動詞（建置、建立、批次…），「建置車道」→「車道」就對得到。
  但同時會產生「樓板」「干涉」「編號」「略過」這種兩個字的核心詞，追問裡太常見
  （聊切割樓板時說「新樓板高度跑掉」，就會被誤切到「建立樓板」）。

### 採用的做法：比較「目前話題」和「其他按鈕」哪邊比較像
- 追問時，同時在目前按鈕的資料、和其他按鈕的資料裡找最像的一段，看相似度差多少。
- 實測 26 句：

  | 類型 | 句數 | 其他按鈕比目前話題高出 |
  |---|---|---|
  | 應該延續的追問 | 18 | 最多 +0.074 |
  | 應該換話題的問題 | 8 | 最少 +0.102 |

- 門檻定 0.09。因為兩群之間只有 0.028 的空隙，超過門檻時**不自動換話題**，而是回問：
  「想確認一下，是繼續問『依列表選取物件』，還是要問別的功能？」並列出候選（建置車道…）。
  判斷錯了，代價只是多點一下。

### 學到
- **每加一個功能（對話記憶），都要回頭檢查它會不會讓別的情況變差。**
- 門檻的空隙很小時，不要讓程式「自己決定」，改成「問使用者」——跟 F1-2 先釐清狀況是同一個原則。
- 同事按的 👎 加上問答紀錄裡的路線欄位，幾分鐘內就定位出原因：回饋機制開始發揮作用了。
