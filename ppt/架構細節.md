# 架構細節：每個步驟背後是怎麼做的

> 給製作投影片的 Claude：原本簡報裡的是「流程圖」，這份說明每個方塊裡面實際怎麼運作。
> 每個步驟分三部分：**做什麼／怎麼做（技術與參數）／為什麼這樣做**。「為什麼」的編號對應 `踩坑與試錯紀錄.md`。
> 配圖在 `架構細節配圖.html`（圖D1～D3）。8 分鐘的簡報放不下全部，建議每個 bot 挑 2～3 個最有內容的步驟講。

---

## 0. 共用基礎

| 元件 | 做法 |
|---|---|
| LINE 介面 | `line-bot-sdk` v3。每個 bot 一個 LINE channel，各有自己的 `WebhookHandler`（用 channel secret 驗證每個請求的簽章，偽造的請求一律拒絕） |
| 伺服器 | 一個 Flask 程式（`webhook_app.py`，port 5000），用網址路徑分流：`/callback/belfast`、`/callback/cec` |
| 對外連線 | cloudflared 把本機的 5000 port 變成公開的 HTTPS 網址，LINE 才送得到 webhook |
| 本機模型 | 全部用 Ollama 在自己電腦跑（RTX 5070 Ti 16GB）：照片和公司資料不外流、沒有 API 費用 |
| 向量模型 | BAAI/bge-m3（中文能力好），透過 LlamaIndex 的 `HuggingFaceEmbedding` 載入，**全程只載一份**，兩個 bot 共用 |
| 向量資料庫 | Chroma（存在硬碟），由 LlamaIndex 的 `VectorStoreIndex` + `ChromaVectorStore` 存取 |
| 一般資料庫 | SQLite：飲食紀錄（`meal_records`）、CEC 問答紀錄（JSON Lines） |

**LINE 的回覆限制怎麼處理**：LINE 給的「回覆權杖」有時效，看圖辨識要 1 分鐘，等不了。
所以 Belfast 先立刻回「處理中」，用背景執行緒跑辨識，跑完再用推播（push）送結果；CEC 回答只要幾秒，
直接回覆，等待時顯示 LINE 的「輸入中」動畫。

## 1. Belfast 熱量秘書（配圖：圖D1）

### 1-1 收照片：先問，不急著算
- **做什麼**：收到照片先跳三個按鈕：「算熱量／我來說熱量／不用了」。
- **怎麼做**：只記下 LINE 的訊息編號，**選了「算熱量」才真的下載照片**；選「我來說熱量」就等使用者打字（例如「炒麵 500大卡」）。
- **為什麼**：有些食物使用者本來就知道熱量（包裝上有寫），不需要每次都跑一分鐘的辨識。

### 1-2 三個模型分別辨識
- **做什麼**：同一張照片給三個視覺模型各自列出「菜名、份量、信心分數」。
- **怎麼做**：
  - 模型：gemma3:12b（Google）、qwen3-vl:8b（阿里巴巴）、minicpm-v（面壁智能），刻意選不同公司，避免錯在同一個地方
  - 提示詞要求：只寫看得到的東西、份量用粗略描述（半碗、一份）不要給公克數、品項名稱盡量具體、每項附 0～1 信心分數、最後附 JSON
  - 溫度 0.1、context 8192；qwen3-vl 要加 `/no_think` 關掉思考模式
  - 不用 Ollama 的「強制 JSON 格式」：實測 minicpm-v 在強制模式下會直接回空陣列；改成讓它自由回答，再用括號配對抓出 JSON
  - 回傳的簡體字用 OpenCC 轉繁體
- **為什麼**：A5（各模型的坑）。

### 1-3 投票：決定照片裡到底有哪些菜
- **做什麼**：把三個模型講的菜歸成同一道，算共識分數，決定哪些計入。
- **怎麼做**：
  1. 歸群第一層：名稱字面相似（一個包含另一個，例如「青菜」和「炒青菜」，或字串相似度 ≥ 0.5）
  2. 歸群第二層：字面對不上的肉類主菜，看肉的種類（禽／豬／牛羊／魚海鮮）；**同一個模型講的兩道菜不合併**（「炸豬排」和「香腸」是兩道）
  3. 共識分數 = 三個模型對這道菜的信心加總 ÷ 3（分母固定 3，某個模型失敗時寧可少抓，不讓單一意見過關）
  4. 分數 ≥ 0.4 → 計入；不到 → 標「疑似誤判」不計入（份量很小的直接捨去）
  5. 菜名取信心加總最高的；平手時聽單獨測試最準的模型（gemma3 > qwen3-vl > minicpm-v）
  6. 沒有任何主菜過門檻、但至少兩個模型說有肉類主菜 → 合併成「主菜（種類未定）」，熱量用候選菜名的中位數
- **為什麼**：A1（兩模型誤殺）、A4（主菜名稱各說各話）。

### 1-4 查熱量（RAG 檢索）
- **做什麼**：每道菜找到「每 100 公克幾大卡」。
- **怎麼做**：依序查，查到就停（配圖：圖D2）：
  1. 衛福部食品營養成分資料庫（2,180 筆）：**完全相同**的品名或俗名
  2. 衛福部資料庫：**向量相似度** ≥ 0.70（LlamaIndex retriever，bge-m3）
  3. 使用者自己回報過的菜：完全相同
  4. 台大自助餐熱量表（83 道）：完全相同
  5. 使用者回報：相近（≥ 0.70）
  6. 台大自助餐熱量表：相近（≥ 0.65）
  7. 都沒有 → 「查無資料」，不硬湊
  - 額外規則：問的名稱沒有「乾」「粉」時，跳過名稱有這兩個字的候選；「土豆」等模糊俗名列黑名單
- **為什麼**：B1（土豆）、B2（字面相似誤導，門檻 0.70 是校準出來的）、B3（花椰菜乾）、B4（完全相同優先）。
  官方資料排第一，因為它是實驗室送檢的數據；台大表標示「僅供參考」，所以排後面。

### 1-5 份量換成公克
- **做什麼**：把「半碗」「一份」「兩顆」換成公克。
- **怎麼做**：
  1. 先查馬偕《食物份量代換手冊》：**單位對得上**才換算（例如手冊寫「顆」、模型也說「顆」）
  2. 單位對不上或查不到 → 典型便當份量表（15 條，每條都有出處；最後一條是泛用主菜 150 公克）：依菜名關鍵字找到類別，例如主食 1 碗 200 公克、
     滷雞腿 150、帶骨雞腿 200、配菜每格 80、雞蛋 55 公克
     - 主菜不管模型說「幾片」都當一份（模型常把切開的同一片排骨說成「幾片」）
  3. 都沒有出處 → 不估算
  - 熱量 = 每 100 公克熱量 × 公克數 ÷ 100
- **為什麼**：C1（91.5 大卡事件）。

### 1-6 信心分級
- **做什麼**：每道菜標一個等級，讓使用者知道這個數字多可靠。
- **怎麼做**：
  - 疑似誤判：投票沒過門檻 → 不計入（**這個判斷放在最前面**，見 A2）
  - 查無資料：資料庫沒有、或份量換算不了 → 不計入
  - 精確對應：衛福部資料庫品名完全相同 ＋ 份量單位對得上（或使用者回報過的同名菜）
  - 相近估算：其他情況（相近品名、典型份量…）

### 1-7 第二種估計：外觀參考
- **做什麼**：不看單一品項，直接用「整盤看起來像什麼」估一個量級。
- **怎麼做**：用 CLIP（openai/clip-vit-base-patch32）把照片轉成影像向量，跟事先算好的 Nutrition5k 3,456 張餐點照片
  （每張都有實驗室實測的總熱量）比 cosine 相似度，取最像的 5 張，回報熱量的中位數與範圍。
- **為什麼**：逐項加總會漏算查不到的菜（偏低），外觀參考不受品項影響，但 Nutrition5k 是美國自助餐，跟台菜外觀有落差，
  所以兩個數字都給、讓使用者選（D3）。

### 1-8 使用者確認與記錄
- **做什麼**：顯示兩種估計，等使用者選「逐項／外觀／手動輸入／不記錄」才寫入。
- **怎麼做**：算好的結果先放在記憶體；寫入時 `raw_json` 一起存兩種估計值、每道菜明細、照片路徑、使用者的選擇。
  手動輸入「菜名 + 熱量」時，這道菜也會加進「使用者回報」知識庫（LlamaIndex 索引），下次辨識到同一道菜就查得到。
- **為什麼**：D1、D2。

### 1-9 文字指令
- **做什麼**：「紀錄」「細節」「刪除今天早上」「這週平均每天攝取多少」，其他就是聊天。
- **怎麼做**：先用固定關鍵字判斷（保證能動作），比對不到才請 llama3.2 判斷意圖（溫度 0）；
  統計功能用 SQL 依日期加總，平均只算有紀錄的天數，並明講這點。

## 2. CEC_API助手（配圖：圖D3）

### 2-1 知識庫匯入
- **做什麼**：把 62 份說明文件（60 個按鈕卡片 ＋ 通用問題 ＋ 功能目錄）存進向量資料庫。
- **怎麼做**：
  - 依 `##` 標題切段，**每段前面補上卡片標題**「# 建立切割樓板（CEC_QuickModeling.CreateFLByCut）」，讓每段都知道自己屬於哪個按鈕；
    超過 1,200 字的段落（功能目錄的大表格）再依行切開，每塊補上表頭 → 共 361 段
  - 每段是一個 LlamaIndex `TextNode`，附 metadata：按鈕英文名、段落名稱、說明頁網址；
    metadata 不併進向量計算（段落文字已經帶了按鈕名稱）
  - 每張卡片是一份「來源文件」：卡片更新時用 `delete(ref_doc_id=檔名)` 一次刪掉舊段落再重建；
    用檔案的 SHA1 判斷哪些卡片變了，伺服器重啟時只重新匯入變動的卡片
- **為什麼**：規格書要求只維護一個知識庫，而不是拆成 60 個；小模型很難判斷該去哪個庫找。

### 2-2 判斷順序：能用程式判斷的，就不讓 AI 猜
每個問題依序檢查，符合就停：

| 順序 | 檢查 | 怎麼做 | 結果 |
|---|---|---|---|
| ① | 說「新問題」 | 關鍵字 | 清掉對話記憶 |
| ② | 不屬於本外掛 | 關鍵字（機電、土木、Autodesk、登不進…） | 從「找誰問」表格查出負責人，直接轉介 |
| ③ | 提到按鈕名稱 | 見 2-3 | 1 個 → 只搜這個按鈕；多個 → 跳按鈕讓使用者選 |
| ④ | 貼上錯誤訊息 | 見 2-4 | 直接取出對應的整段 |
| ⑤ | 正在聊某個按鈕 | 對話記憶 | 當成追問，只搜這個按鈕 |
| ⑥ | 通用問題（灰色、授權、安裝、Excel…） | 關鍵字 → 指定段落 | 直接取「按鈕是灰色的不能按」等段落 |
| ⑦ | 「有沒有功能可以…」 | 關鍵字 | 搜功能目錄 ＋ 全部 |
| ⑧ | 以上皆非 | — | 回問「是哪個功能」，附 3 個可能的按鈕 |

### 2-3 按鈕名稱比對（容錯）
- **怎麼做**：
  - 名單：每張卡片的中文名、英文名、別名
  - 正規化：全形轉半形、轉小寫、去空白標點、常見錯字統一（梁→樑、驅→軀、版→板）
  - 先找「名稱完整出現在問句裡」；找不到才試打錯字：**同長度、恰好錯一個字**
  - 比對到的詞如果也是別的按鈕名稱的一部分（「切割樓板」⊂「建立Deck切割樓板」）→ 一併列為候選讓使用者選
  - 同時命中好幾個時，被別的命中「包含」的短命中拿掉（問「建立Deck切割樓板」就不會再跳出 RC 版）
- **為什麼**：F2（比對太寬或太嚴）。

### 2-4 錯誤訊息比對
- **怎麼做**：匯入時把所有卡片「錯誤訊息對照」裡用「」框起來的原文抓出來（共 332 條），去掉空白、標點、`xxx` 和數字（ID）；
  使用者貼的文字做同樣處理後，看原文有沒有出現在裡面。命中就用 LlamaIndex 的 `get_nodes` 依條件把那幾段**整段取出**。
- **為什麼**：E2（向量檢索把正確段落排到第 3、或漏掉）。

### 2-5 向量檢索
- **怎麼做**：LlamaIndex retriever，取前 4 段；搭配 `MetadataFilters`（按鈕英文名 `in [...]`）把範圍限定在比對到的按鈕 ＋ 通用問題。
- **為什麼**：範圍限定之後，不會被別的按鈕的相似段落混進來。

### 2-6 生成回答
- **怎麼做**：
  - 模型 qwen3:8b，關閉思考模式，溫度 0.1
  - 提示詞順序：參考資料 → 找誰問 → 先前對話 → 使用者問題 → **規則（放最後）** → 「回答：」
  - 規則重點：只能根據參考資料、不可以把不同條拼湊成建議、沒資料就說沒資料、條列式手機好讀、不要寫網址
  - 回答後處理：刪掉模型自己寫的網址行；說明頁連結由程式從 metadata 附上（最多 2 個）；簡體字只轉換知識庫沒用過的字
- **為什麼**：E3（規則放後面）、E4（換模型）、E5。

### 2-7 對話記憶
- **怎麼做**：每位使用者一筆狀態（存在記憶體）：目前的按鈕、最近 2 輪問答、最後說話時間。
  - 沒提到按鈕的追問 → 延續目前的按鈕；提示詞附上最近 2 輪問答
  - 換按鈕（提到別的按鈕、選了別的按鈕、錯誤訊息屬於別的功能）→ 先清掉舊的問答紀錄
  - 15 分鐘沒說話或說「新問題」→ 重設
  - 延續話題時，回答最後標示「延續『○○』的問題」
- **為什麼**：F1（使用者實測回饋）。

### 2-8 紀錄與維護
- 每次問答寫進 `qa_log.jsonl`（問題、走哪條判斷路徑、回答）→ 可以找出「常被問、但資料裡沒有」的題目，回頭補卡片
- 公司內部資料（同仁姓名、內部連結）不進 git
