00 本次決策摘要

份量資料來源：3 主 1 輔

份量估算是整個專題最大的坑，決定用「人機協作」取代精確影像測量：模型先給份量假設，使用者用 LINE Quick Reply 一鍵修正。

主｜衛福部食物份量代換手冊 輔｜Nutrition5k（校準錨點）

延續的設計原則

  • 熱量必須查資料庫得出，查無對應品項時誠實回覆「無法確定」
  • 依對應精確度分三級信心標示
  • 數值計算相關生成一律低溫度
  • 明顯超出飲食範疇的提問（如醫療診斷）拒答並建議諮詢專業人士

A 知識庫

清洗熱量資料、結構化份量對照表，是後面所有檢索的地基。

A1衛福部食品營養成分資料庫清洗匯入

下載衛福部食品營養成分資料庫，清洗品項名稱／熱量／三大營養素欄位，統一單位為 kcal/100g，轉成 Document 匯入 Chroma collection nutrition_db。結果：找到 data.gov.tw 上的官方開放資料匯出，清洗出 2,180 筆、涵蓋全部 18 大類，抽樣 10 筆對官網核對 10/10 完全吻合。

✅ 已完成依賴：無

測試方式抽樣 10 筆對官網逐一核對，10/10 吻合；53 筆缺蛋白質/脂肪數據標成 null(未測量)非 0。檔案在 data/nutrition_db/。

A2食物份量代換手冊結構化（主要來源）

拆解 2023 版《食物份量代換手冊》PDF，整理成「食物類別／份量描述／生活化比喻／對應公克數」表格，匯入獨立 collection portion_reference。結果：手冊是圖片排版，改用視覺逐頁核對，30 筆數字全部對到手冊原始頁碼。過程中發現並更正一個重要錯誤：水果並非固定「1份=100公克」，而是固定「醣15公克」，不同水果對應公克數差很大(芭蕉45g~小番茄220g)。

✅ 已完成依賴：無

測試方式逐頁核對手冊原始頁碼，30 筆中 29 筆 confidence 為 high。細節與版本記錄見 data/portion_reference/NOTES.md。

A3Nutrition5k 整餐校準錨點（架構升級，不再是輔助項目）

結論：完成，且找到一個「0 大卡」案例證明了它的價值。從 Nutrition5k 公開 bucket 直接用 HTTPS 抓俯視照片+metadata(不需要 gsutil)，下載 3,456 張、建成 CLIP(clip-vit-base-patch32) 相似度索引(3,444 道菜)。過程中踩到一個 transformers 版本 API 變更的 bug：get_image_features() 回傳格式跟舊版不同，要從 .pooler_output 才能拿到正確的 512 維向量，一開始拿錯導致維度對不上直接報錯。測試發現「images (6).jpg」這張照片已知品項加總是 0 大卡(全部查無資料)，靠校準錨點還能給「約 212 大卡(範圍 160~945)」的量級參考——這正是這個功能存在的意義：資料庫完全幫不上忙時，還有一個有真實資料依據的備案，而不是兩手空空。

✅ 已完成依賴：無

測試方式10 張真實照片的最近鄰查詢，跟 C3 的已知品項加總並列比較，詳見 data/nutrition5k/A3_REPORT.md。

A4補充知識庫：台大自助餐熱量表（2026/9/27 新增，實測驅動）

結論：完成，凌晨實機測試發現 8 項裡 7 項查無資料後緊急補上的。國立臺灣大學膳食協調委員會《熱量表【盤菜/自助餐類】》83 筆，直接補上 TFDA 缺的複合菜餚(糖醋排骨/炒青菜/炸豆腐等)。這份資料可信度比 TFDA 低(來源頁面自己寫「僅供參考」)，刻意做成獨立 collection，只有 TFDA 查無品項才退而求其次查這裡，信心度標成 exact_secondary／similar_secondary，回覆文字會註明「非官方送檢數據」。門檻另外校準(0.65，比 TFDA 的 0.70 寬鬆)，因為測出雜訊分數上限只有 0.59，安全間隔比 TFDA 當初的案例健康很多。拿實測真實失敗案例回測：8 項修好 4 項(糖醋排骨/炒青菜/炸豆腐/叉燒飯)。

✅ 已完成依賴：C1

測試方式拿凌晨實測的真實失敗品項回測，8 項修好 4 項；另用雜訊詞校準門檻。詳見 data/composite_dishes/A4_REPORT.md。

B 視覺辨識

讓多模態模型吐出穩定、可解析的辨識結果，而不是自由發揮的一段話。

B1Ollama 多模態模型選型

結論：選用 minicpm-v。llama3.2-vision 因目前 Ollama 版本(0.33.3)不支援其 mllama 架構，模型載入直接失敗(10/10 HTTP 500)，已排除，與 prompt 無關。llava 內容偏籠統，且 10 張中 2 張陷入無限重複輸出(27~32 秒才被截斷)，改強制 JSON schema 後問題更嚴重。minicpm-v 辨識內容明顯更具體準確、速度最快(平均 3~4 秒)，10/10 無重複問題，列為主要模型；llava 留作備案。

✅ 已完成依賴：無

測試方式10 張測試照片 × 3 模型完整比較，詳細數據見 data/vision_benchmark/B1_REPORT.md

B3雲端視覺方案評估：Gemini API

本地 minicpm-v 有套模板/幻覺問題(見 B1/B2)，考慮把「辨識」這一步換成 Gemini API，其餘(RAG 檢索、C1~C3 計算)完全不動——架構上只需替換 src/food_recognition.py 一個檔案。已釐清：消費版 Gemini Pro/Advanced 訂閱跟 API 是分開計費的兩件事，需另外在 Google AI Studio 申請 API key。2026/4 起 Pro 模型退出免費層，但 Flash／Flash-Lite 仍免費，額度對這個專題的用量綽綽有餘。背景研究(2026/9)補充：找到一篇用 Nutrition5k 資料集做的食物辨識+熱量估算 benchmark，顯示 Gemini 3.1 Flash Lite 性價比可能比 Flash 更好(準確度接近最高、食材辨識反而全場最強、成本最低)，值得兩個都測。另外確認 llama3.2-vision 在 Ollama 上的問題是官方已知未修復 bug(GitHub #16547)，不用等它自己修好。多找到一個本地候選 qwen3-vl:8b(中文原生訓練資料多)，可作為 Gemini 的免費對照組。

👤 需申請 API key🤖 串接可執行依賴：B2

B2結構化辨識 Prompt 設計

格式問題已解決，但發現新的準確度問題。自由輸出+平衡括號擷取 JSON、OpenCC 簡轉繁，10/10 解析成功、0 簡體殘留(見 src/food_recognition.py)。但逐張核對辨識內容後發現 minicpm-v 對「台式便當」有明顯套模板傾向——10 張裡 6 張都寫「糖醋排骨」，即使實際是滷雞腿或炸豬排；還有一次幻覺出照片裡沒有的「南瓜」。格式工程完成 ≠ 辨識可靠，這兩件事要分開驗收，且此問題會直接影響 C1 的檢索設計。

B4多模型集合辨識與投票評分（新規劃）

結論：投票機制成功，但有延遲代價。本地 minicpm-v + qwen3-vl:8b 雙模型投票。過程中抓到一個關鍵 bug：qwen3-vl 預設「思考模式」會把整個 context 全部拿去內部推理，永遠生不出最終 JSON 答案(10張裡8張失敗)，加 /no_think 關閉思考模式後 10/10 正常。投票結果驗證了 B2 發現的問題是真的：minicpm-v 對 10 張裡 8 張都講「糖醋排骨」，但 qwen3-vl 給的答案完全不同(烤雞腿/溏心蛋/涼拌捲心菜等)，投票機制正確把這種分歧標成「單一模型」低信心，沒有照單全收。代價：辨識時間從單模型 3~4 秒變成集合 25~60 秒，正式接回 D2 時 LINE 同步回覆恐怕來不及，需要改用 push API。

✅ 已完成依賴：B2

測試方式10 張測試照片雙模型投票，10/10 成功，字串相似度分群運作良好。詳見 data/vision_benchmark/B4_REPORT.md。

C RAG 檢索與計算引擎

把辨識結果換成有資料庫依據的熱量數字，並誠實標示信心程度。

C1食物名稱檢索與比對邏輯

結論：語意檢索門檻設 0.70(保守)。用 bge-m3 + Chroma 對 nutrition_db 建索引，精確比對(品項名稱/俗名)優先，其次語意檢索。校準時發現 bge-m3 對短食材詞常被字面重疊誤導(「小黃瓜片」最高分是「小黃魚」、「炸雞腿」最高分是「炸雞粉」)，門檻定太低會把錯誤類別包裝成「相近品項」，故保守定在 0.70。校準過程中還抓到一個真實 bug：「土豆」被精確比對到花生(553 kcal/100g)而非馬鈴薯(77 kcal/100g)，熱量差 7 倍，已修掉。拿 B2 真實辨識結果驗證：精確對應 42%、相近品項 8%、查無品項 50%——查無品項偏高是因為 TFDA 資料庫偏原始食材、B2 常給複合菜名，印證了 TODO.md 最初就列的「連鎖店/超商菜單」待辦缺口，非檢索邏輯有誤。2026/9/27 補充：曾嘗試借鏡 DietAI24 的「類別不相容門控」概念，用語意分數做通用的合理性檢查取代黑名單，但實測後放棄：已知有問題的「土豆」語意分數 0.6477，另一個完全合法的「地瓜葉」只有 0.6607，只差 0.013，找不到安全門檻能兩者兼顧。結論是保留逐案例維護的黑名單，已跑過完整驗證確認沒有回歸。

✅ 已完成依賴：A1、B2

測試方式混淆測試集(完全對應/模糊相近/完全不相關)校準門檻；B2 真實 24 個辨識品項端對端驗證。詳見 data/nutrition_db/C1_REPORT.md。

C2份量描述轉換公克數邏輯

結論：先比對單位種類，單位不合寧可承認不確定。「半碗」跟手冊的「1份(兩湯匙)」是完全不同的單位系統，直接相乘會嚴重低估，所以先解析辨識詞的單位(碗/份/顆/根/片/湯匙/茶匙)，跟 portion_reference 比對，單位相容才換算，不合只給基準值當參考。另外發現 nutrition_db(TFDA 18類)跟 portion_reference(六大類)兩套分類系統對不上，用退回全表比對繞過。

✅ 已完成依賴：A2、B2

測試方式B2 真實 33 組(食物,份量)配對端對端測試：可信換算 15%、單位不合 24%、無法估算 61%。詳見 data/portion_reference/C2_REPORT.md。

C3熱量估算與信心標示組裝

結論：格式跟信心標示都正確，但發現總熱量普遍嚴重低估。10 組真實案例測試，回覆格式(品項/份量假設/資料來源/信心標示/總熱量)全部正確，查無資料項目誠實排除且會提醒「未計入,實際熱量可能更高」。但總熱量全部落在 91.5~222.8 大卡，遠低於便當實際的 600~900 大卡——不是算錯，是主菜類幾乎都查無資料、白飯又卡在單位不合只能用最小基準值，兩個原因疊加的必然結果。這代表現在的總熱量數字還不能當作使用者信賴的最終答案，得在 D 層 UI 上把這件事講清楚，且指向「知識庫覆蓋率」才是真正瓶頸，不是這幾張卡片的邏輯問題。

✅ 已完成依賴：C1、C2

測試方式端對端跑 10 組真實案例，人工檢查回覆格式、信心標示、總熱量揭露語是否正確。詳見 data/vision_benchmark/C3_REPORT.md 與 c3_sample_replies.txt。

2026/9/27 抓到並修好一個嚴重漏洞：接回 D2 時，把 B4 集合投票算出的「共識品項／單一模型」資訊直接捨棄了，導致 B4 最重要的防呆(偵測套模板幻覺)完全沒發揮作用。實機測試真的抓到「糖醋排骨」被 minicpm-v 單獨講出來、qwen3-vl 完全沒附和，資料庫(A4)剛好又查得到「糖醋排骨」的熱量，兩個問題疊加下差點把一個幻覺出來的菜當成有效資料算進總熱量。修法：新增「疑似誤判」信心等級，只要是「單一模型」講的品項，不管資料庫查不查得到，一律不計入總熱量，且獨立於「查無資料」顯示，讓使用者知道這是「模型可能認錯」而不是「資料庫沒收錄」。

C4整合估算：已知品項加總 + 整餐校準錨點（新規劃）

結論：完成。最終回覆同時列出 C3 算出的「已知品項加總(下限)」+ A3 提供的「視覺最相近參考餐點的已知真實總熱量(校準區間)」，兩個數字都有真實資料依據。10 張測試照片平均下限約 127 大卡、錨點中位數約 380 大卡，兩者的落差誠實反映資料庫查不到的品項(通常是主菜)貢獻了多少熱量。刻意不採用「另一個模型綜合份量/食物內容/照片直接生成總熱量」的做法——那等於讓模型憑感覺補洞，違反 TODO.md「不能讓模型自己編熱量數字」的核心原則。

✅ 已完成依賴：A3、C3

測試方式10 張真實照片端對端測試，人工核對回覆文字是否清楚區分兩個數字的意義，詳見 data/vision_benchmark/c4_sample_replies.txt。

03 怎麼把任務交給其他 AI

不需要 Claude Desktop——CLI 現在就有兩種分工方式，卡片上的 🤖／👤 標籤就是照這個邏輯標的。

方法一・同一個 session 內開 subagent

由這個對話直接開子代理平行處理範圍明確的任務（例如「拆解衛福部 PDF 轉成表格」），結果整理後回報給我，不會佔用你看到的對話 token。適合大多數標「🤖」的卡片。

方法二・跨 session 的 teammate 訊息

你電腦上其實已經有另一個閒置的 Claude Code session pyrag-f5，根目錄推測就是 D:\pyRag——正是這份課程教材所在的位置。可以直接把 A 系列（知識庫）工作透過訊息轉交給它，因為環境與資料都已經在那邊，不用重新設定。這就是「多 AI 協作」實際的運作方式：每個 terminal 開一個獨立 session，各自有自己的 context 與 token 額度，彼此用訊息交接任務。

為什麼不需要 Desktop

Desktop 版沒有 subagent／跨 session 訊息這套工具，對話是持續累積的長 context，缺少 CLI 這種工具化的自動壓縮機制——這也是你先前用 Desktop 問幾個問題就比較快燒 token 的原因，是產品定位不同，不是設定問題。
